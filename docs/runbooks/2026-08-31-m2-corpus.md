# Runbook: producing the M2 real-corpus number

Implements `docs/superpowers/specs/2026-08-31-m2-calibration-design.md` (Half A).
Everything below runs from `trainer/` with the venv python.

## 0. Credentials

`PROD_APP_ID` and `PROD_EBAY_CERT_ID` must be in the environment. They live in
the gitignored `.env` at the repo root. Export them yourself before any step
below reads them — do not put the actual values in this runbook, in the
manifest, in the audit sheet, or in any log. The production keyset works
because `workers/ebay-account-deletion/` is deployed and accepted by eBay — if
OAuth starts returning `invalid_client`, check that endpoint before the
credentials.

```bash
set -a && . ../.env && set +a
```

## 1. Rebuild the catalog database

**This checkout has no `data/catalog.sqlite`.** `data/` under `trainer/` holds
only `images/` (3.2 GB, 170 set directories) and `index/` (`cards.bin` +
`cards.bin.ids.json`, 66 MB) — the expensive, already-built artifacts survived;
only the sqlite metadata db is gone, and every later step in this runbook
(`corpus.build`'s card lookup, `eval.real`'s `--db`) expects it at its default
path. Rebuild it before anything else:

```bash
cd trainer
.venv/bin/python -m hitcheck_trainer.catalog.cli sync \
    --db data/catalog.sqlite --images data/images
```

This is `hitcheck_trainer/catalog/cli.py`'s `sync` command; `--db` and
`--images` above are its own defaults (`DEFAULT_DB = "data/catalog.sqlite"`,
`DEFAULT_IMAGES = "data/images"`), spelled out here so this step doesn't
silently depend on whichever directory happens to be current. The sync is
resumable — it checkpoints card metadata as it goes and only re-fetches images
missing or zero-byte on disk, so with `data/images/` already present this step
should re-populate the sqlite quickly without re-downloading the 3.2 GB.
Rerun it if it reports a failure; it picks up where it left off.

Do not attempt this rebuild as part of any other step — run it first, in
isolation, and confirm it exits 0 before moving on.

## 2. Acquire the corpus

```bash
cd trainer
set -a && . ../.env && set +a
.venv/bin/python -m hitcheck_trainer.corpus.build --target 600
```

Costs roughly two Browse calls per candidate against a ~5,000/day budget.
Rerunning tops the corpus up: it skips any itemId already accepted into the
manifest, and it leaves already-downloaded images alone.

**A rerun over-counts discards.** Dedup only applies to *accepted* listings
(`seen = manifest.item_ids()` in `build.py`) — a listing that was previously
discarded is not remembered as such, so a rerun that resurfaces it re-fetches
it and increments its discard reason a second time. This is accepted-as-
designed, not a bug: fixing it would mean tracking discarded ids forever.
It means the `kept=... discarded=...` breakdown printed by a corpus built
across multiple runs is **not** one-attempt-per-listing — do not read it as
the acceptance rate of a single pass. Read the `kept=...` figure and the
overall shape of the breakdown, not the discard total, as the signal for
whether the resolver is behaving.

## 3. Hand-crop

```bash
.venv/bin/python -m hitcheck_trainer.corpus.croptool
```

Open http://127.0.0.1:8765/. For each photograph, drag a box roughly
around the card, then drag each of the four numbered corners onto the
**card's** corners — the card, not the slab, not the label. `space` saves
and loads the next card; `u` clears the quad so you can start the drag
over. Progress saves after every card, so stop and resume as often as you
like.

**Corner 1 belongs on the card's top-left.** It is drawn yellow because it
is the one thing no server-side check can catch: a quad rotated a quarter
turn is still four-sided and still clockwise, and produces a sideways crop
that can never retrieve its own catalog scan. On a card photographed at an
angle, pick the corner that is top-left *of the card*, then work round it.

Winding is safe by construction — the rubber band emits its corners
clockwise — so `validate_quad`'s counter-clockwise rejection now only
fires if a corner is dragged past its neighbours. If it does fire you get
an alert and the quad stays on screen; drag the offending corner back
rather than re-marking the card.

`s` **skips** the current photograph, permanently. Use it when the image
will not render (a blank, unclickable canvas means the downloaded body is
not a decodable image) or when no card is visible in the frame. Skips are
recorded in `data/corpus/skipped.json` beside `crops.json`, so a later run
of the tool will not serve that entry again. A skipped entry has no quad,
so `eval.real` and `corpus.audit` treat it exactly like an uncropped one —
it simply never enters the eval, and it is not counted as crop progress.
Skipping reduces N, so if you find yourself skipping many, raise `--target`
in step 2 and acquire more rather than accepting a short run.

This is the expensive step: a few hundred cards. It exists because M3's
detector does not, and it doubles as ground truth for evaluating M3 later.

A partial `crops.json` is the normal mid-pass state — `eval.real` and
`corpus.audit` both simply skip any manifest entry with no crop yet; neither
treats an incomplete crop pass as an error.

## 4. Audit the labels

```bash
.venv/bin/python -m hitcheck_trainer.corpus.audit --count 50
```

Open the printed path. Count the pairs that are not the same card. That
count is the input to the bound; do not re-roll the seed to get a nicer
number — the sample is seeded specifically so it cannot be repeated until it
produces a flattering count.

## 5. Run the eval

```bash
.venv/bin/python -m hitcheck_trainer.eval.real --reuse-index \
    --label-errors <N> --label-sample 50
```

`--reuse-index` is not optional in spirit: the point is to search the same
gallery the synthetic run searched, so any difference in the number belongs
to the queries. If `--index` is mistyped, or the `cards.bin.ids.json`
sidecar is missing, the run **stops with an error naming the missing path**
rather than quietly rebuilding — a silent rebuild would overwrite the 66 MB
`data/index/cards.bin` and measure against a different gallery than the
synthetic run, breaking the very comparison this step exists to make. Drop
the flag only if you intend to rebuild the gallery.

`main()` refuses to print a verdict below 500 usable queries
(`MIN_QUERIES` in `eval/real.py`) — it still prints the accuracy and interval,
but treat that as a signal to crop more, not as the answer.

## 6. Record the result

Write `docs/verification/2026-08-31-m2-real-corpus.md` alongside
`2026-08-10-m2-zeroshot.md`. It must state:

- top-1, top-5, the 95% interval, and the verdict.
- The label-error bound and the audit sample it came from.
- The corpus yield line from the manifest, so the selection bias is visible.
- That the number is measured **given a good crop** (hand-cropped; M3 does
  not exist), and therefore conditional on M3 working.
- That seller photographs are well-lit, static and high-resolution —
  meaningfully easier than a compressed handheld stream frame — so this is
  an **upper bound**.
- That the corpus is described qualitatively as "seller photographs" until
  Half B's `measure.py` exists to place it on the degradation axes.

## If the verdict is INCONCLUSIVE

That is an answer, not a failure. The interval straddles 0.90 and the
sample cannot resolve which side it is on. The decisive bands are:

| N | SKIP_TRAINING needs top1 ≥ | TRAIN_REQUIRED needs top1 ≤ |
|---|---|---|
| 500 | 0.9280 | 0.8720 |
| 1000 | 0.9190 | 0.8810 |
| 2000 | 0.9135 | 0.8865 |

Go back to step 2 with a higher `--target` and crop the additions. Do not
lower the threshold, and do not quote the point estimate as if it settled
the question.
