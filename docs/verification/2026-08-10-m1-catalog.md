# M1 catalog sync — verification (2026-08-10)

Real run of `python -m hitcheck_trainer.catalog.cli sync` against the live
`api.pokemontcg.io` and `images.pokemontcg.io` hosts, from `trainer/`.

## Final result

| Metric | Result |
|---|---|
| Cards in `data/catalog.sqlite` | 20,479 / 20,479 (100%) |
| Cards with an image URL | 20,479 |
| Images downloaded successfully | 20,427 |
| Images permanently failed (HTTP 404) | 52 |
| `data/images` size | 3.2 GB |
| `.part` temp files left behind | 0 |

The CLI's own exit code reflects this correctly: the final run exits `1`
and prints
`*** INCOMPLETE: 52 image(s) failed to download. Rerun the sync to retry
them. ***` — this is expected to never turn into a clean `0` exit, because
the 52 failures are not transient (see below).

Card count and every card having an `image_small` URL match expectations
from the brief (20,479 cards). Total download size (3.2GB) is larger than
the brief's ~700MB–1GB estimate; see "Deviation" below — this is real
measured data, not a bug.

## Reruns needed

**Metadata sync:** 5 runs of the full CLI.
- Run 1: 0 → 3,500 cards, then `CatalogApiError` (page 4, 6 attempts, all 500s exhausted)
- Run 2: 3,500 → 5,500 cards, then page 23 exhausted retries (last status 500)
- Run 3: 5,500 → 8,250 cards, then page 34 exhausted retries (last status 502)
- Run 4: 8,250 → 16,000 cards, then page 65 exhausted retries (last status 500)
- Run 5: 16,000 → 20,479 cards — metadata complete, then proceeded straight
  into the image phase and downloaded 20,427/20,479 images in one pass
  (52 failed).

So metadata needed 4 reruns after the first attempt (5 total invocations)
to get all 82 pages down. Each failure was `CatalogApiError` (retries
exhausted after 6 attempts per page), i.e. a run of 500/502 responses long
enough to outlast the backoff schedule — consistent with the ~50%
per-request failure rate noted in Task 8/README, since `P(6 straight
failures) ≈ 1.6%` per page and there are 82 pages.

**Image download:** the first full pass (inside run 5) got 20,427/20,479
(99.75%) on the first try. 9 further reruns (runs 6–14) were then executed
automatically by the rerun loop; every one of them reported the *exact
same* `0 downloaded, 20,427 already present, 52 failed` — i.e. zero
progress across 9 consecutive attempts. That determinism is the signal
that these are not flaky-host failures.

## Failure pattern

**Metadata (transient):** upstream 500/502 errors on the paged
`/v2/cards` endpoint, consistent with the ~50% failure rate measured
earlier. `CatalogApi` retries each page up to 6 times with backoff before
giving up; when it does, `sync_catalog` has already committed and
checkpointed every fully-read prior page, so each rerun picked up exactly
where the last one stopped (no re-fetching of already-synced pages,
confirmed by the progress counters above never resetting).

**Images (52 permanent failures, not flakiness):** direct `curl -o
/dev/null -w '%{http_code}'` against the failing URLs (e.g.
`https://images.pokemontcg.io/ecard2/67.png`,
`https://images.pokemontcg.io/mcd14/1.png`) returned **404**, not 500/502.
404 is correctly excluded from `images.py`'s `RETRYABLE` set, so the
downloader does not waste attempts on it — but it also means no number of
reruns will ever fetch these files; the CDN genuinely does not have them.
All 52 IDs:
- The complete McDonald's promo sets `mcd14` (12 cards), `mcd15` (12),
  `mcd17` (12), `mcd18` (12) — 48 cards, entirely missing images.
- 4 singles: `ecard2-67`, `ex5-102`, `hsp-HGSS18`, `svp-102`.

This is an upstream data gap in `images.pokemontcg.io`, not a bug in the
sync code or a transient network issue. Given this is real and reruns
cannot fix it, the loop was stopped after run 14 rather than run
indefinitely; see "Deviation" below.

## Deliberate interrupt-and-resume test

To prove resumption works in practice (not just in the unit tests), after
the catalog was otherwise complete:

1. Deleted 1,000 already-downloaded image files directly from disk
   (`data/images/...`), forcing a real re-download window on the next run.
2. Started `uv run python -m hitcheck_trainer.catalog.cli sync` in the
   background. It skipped metadata (already complete) and began
   re-downloading the deleted images.
3. Once progress reached image 1,277/20,479 (mid-download), sent
   `SIGINT` (`kill -INT`) directly to the Python subprocess — the
   Ctrl-C equivalent requested by the brief.
4. Verified: process terminated on `KeyboardInterrupt`; **0 `.part`
   files** left on disk (the atomic write-then-rename in `images.py`
   held); 19,802/20,479 images present (some of the 1,000 deleted ones
   had already been re-downloaded before the interrupt, the rest were
   still missing).
5. Reran the CLI. Result: `625 downloaded, 19,802 already present, 52
   failed` — 625 + 19,802 + 52 = 20,479 exactly. The rerun downloaded
   precisely the files still missing after the interrupt, re-skipped
   everything already on disk, and landed on the same 52 permanent
   failures as before. No duplicate work, no corruption, no data loss.

Resumption works as designed for both the metadata phase (page-level
checkpointing) and the image phase (per-file existence + atomic-write
skip logic).

## Deviations from the brief

- **Image directory size (3.2GB, not 700MB–1GB):** the brief's estimate
  was low. Measured: the `images.small` variant actually served is
  240×330 PNG, averaging ~163KB/file (confirmed via `PIL.Image.open` and
  the CDN's `Content-Length` header), not the smaller size implied by the
  estimate. 20,427 files × ~163KB ≈ 3.2GB, which matches `du -sh`
  exactly. No code change was needed — this is a measurement update, not
  a defect.
- **Sync cannot reach exit 0:** the design (per the task brief's mandatory
  requirement) is that the CLI exits non-zero whenever
  `len(pairs) - downloaded - skipped > 0`, so a partial run is never
  mistaken for done. Because 52 images are permanently 404 upstream, this
  catalog will *always* exit 1 on the image phase, no matter how many
  times it's rerun. This is working as designed — it correctly refuses to
  report false success — but it means "rerun until exit 0" is not
  achievable for this dataset as it stands. 20,427/20,479 (99.75%) of
  images are present; the 52 missing cards are documented above for a
  training-time decision (skip them, or backfill from another source).
- Stopped the automated rerun loop after 14 iterations (5 to finish
  metadata + first image pass, 9 more that produced byte-identical
  `0/20427/52` results) once curl confirmed the 52 failures are
  permanent 404s rather than flaky-host retries. Continuing to rerun
  indefinitely would not change the outcome and was not useful evidence.
